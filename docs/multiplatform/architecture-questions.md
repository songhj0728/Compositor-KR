# Architecture questions — decisions

Every question raised by [core-api.md](../core-api.md) and the [migration plan](document-model-inventory.md), with the
decision taken on 2026-09-30 (baseline: Compositor-KR 1.4.5, build 40). Each lists why, what it means for Windows
performance, for macOS, for the migration, and whether it can be reversed. The full reasoning for the large ones is in
[windows-architecture.md](windows-architecture.md). Nothing is left "TBD"; where a permanent answer needs evidence
that doesn't exist yet, the decision is the safest temporary form and says what will finalize it.

Reversibility: **Yes** — can change later without user-visible or format impact; **Costly** — possible, with real
rework; **No** — effectively permanent (persisted data or published artifacts depend on it).

---

### Q1 — Core ID type
- **Decision:** a Core-owned 128-bit value type (`LayerID`, `DocumentID`, `GuideID`), generated by the Core as random
  UUID version 4 from the platform CSPRNG (`std::random_device` → `RtlGenRandom` on Windows, `arc4random` on macOS),
  written as uppercase UUID strings exactly as `.comp` does today.
- **Why:** C++ Core (Q11) has no platform UUID type; the string form keeps every existing file valid.
- **Windows:** 16-byte trivially-copyable value; no allocation, no platform call per ID except generation.
- **macOS:** the Swift wrapper converts to/from `UUID` at the edge; `.comp` bytes unchanged.
- **Migration:** wave 4 of the dependency map; golden `.comp` tests guard the string form.
- **Reversible:** representation **Yes** (internal); string format **No** (persisted).

### Q2 — Foundation in the Core
- **Decision:** not applicable to a C++ Core: the Core uses the C++ standard library only, plus vendored, pinned
  header-only libraries named in windows-architecture.md (JSON, LittleCMS is platform-side). No Foundation, no platform
  SDK. The macOS Swift wrapper may use Foundation — it is platform code.
- **Why:** removes the 5.8–63 MB Swift/Foundation runtime question entirely and the `CGFloat`-only-in-full-Foundation
  trap.
- **Windows:** no runtime to ship or load. **macOS:** none. **Migration:** none. **Reversible:** Yes.

### Q3 — Who encodes the manifest JSON
- **Decision:** the **Core** reads, validates and writes `manifest.json` (records, version gating, ranges, references,
  defaults) with a vendored header-only JSON library, pinned; the platform does package I/O and PNG codecs.
  Compatibility is **semantic**, not byte-for-byte: key order and number formatting may differ from Swift's
  `JSONEncoder` (numbers are written shortest-round-trip via `std::to_chars`), and golden tests compare parsed values.
- **Why:** one implementation of the format's rules for both OSes; byte identity between two JSON writers is neither
  needed by any reader nor achievable cheaply.
- **Windows:** manifests are ≤ 4 MiB; parse cost is negligible next to PNG decoding. **macOS:** reads C++-written
  manifests through the same validation. **Migration:** step 0 golden tests become semantic comparisons.
- **Reversible:** Yes (library choice internal).

### Q4 — `ImageRef` pixel formats
- **Decision:** `RGBA8` premultiplied and `Gray8` now; the format enum reserves `RGBA16F` premultiplied (and `RGBA32F`)
  for future high-bit-depth/HDR work; consumers must reject formats they don't support with an error, not a crash.
- **Why:** `.comp` stores 8-bit PNGs and the renderers composite in 8-bit today; reserving the values costs nothing.
- **Windows:** `R8G8B8A8_UNORM`/`R8_UNORM` textures map 1:1, no conversion on upload. **macOS:** same as today.
- **Migration:** wave 5. **Reversible:** Yes (additive).

### Q5 — Who owns pixel memory
- **Decision:** the **Core** owns every `ImageRef`'s CPU storage (tiles), allocating through a platform allocator hook
  (`VirtualAlloc`/`mmap` for large blocks). A platform may also wrap a buffer it produced (a decoded PNG) with a
  release callback so import doesn't copy. GPU memory belongs to the renderer only.
- **Why:** one owner makes lifetime explicit across the C ABI; wrapping avoids a copy on import.
- **Windows:** large aligned blocks, no per-pixel allocation, no copy at the boundary. **macOS:** `CGImage` becomes an
  edge representation wrapping tiles (`CGDataProvider`) instead of the storage.
- **Migration:** wave 5 (the `ImageRef` step). **Reversible:** Costly.

### Q6 — Snapshot implementation
- **Decision:** persistent, structurally shared state: layers are immutable nodes held by reference-counted pointers in
  a chunked persistent vector; a snapshot is a root pointer plus `Revision`. The flat layer table of core-api §8 is
  built lazily per snapshot and reuses unchanged rows from the previous table.
- **Why:** meets core-api §8.4 at 10,000 layers without copying the document per snapshot or per undo step — what
  Swift's copy-on-write gave the macOS app for free, made explicit.
- **Windows:** snapshot = O(1) pointer copy; table rebuild O(changed layers). **macOS:** same Core.
- **Migration:** Core track C2. **Reversible:** Yes (internal).

### Q7 — Change notification
- **Decision:** **no callbacks from the Core.** The owner thread knows when it mutated and calls `changes(since:)`; the
  renderer pulls the latest snapshot each frame (atomic hand-off, latest wins). Job completion is announced by the
  platform's job system to its own UI dispatcher, not by the Core.
- **Why:** keeps the Core free of UI re-entrancy and threading surprises; costs one cheap call per update.
- **Windows:** no cross-thread callbacks into C#; no marshaling of callbacks. **macOS:** same. **Reversible:** Yes
  (a callback could be added later, but isn't needed).

### Q8 — Selection representation
- **Decision:** `CorePath` only, exactly as today (Magic Wand, Color Range and Object Selection all hand back a path;
  the wand via `MaskTracing` at 50%). The contract reserves an optional raster `SelectionMask` (`Gray8` `ImageRef`) for
  soft selections later.
- **Why:** preserves current behavior precisely; the reserved field avoids a breaking change later.
- **Windows:** path rasterized to coverage on the GPU when needed. **macOS:** unchanged. **Migration:** wave 6.
- **Reversible:** Yes (additive).

### Q9 — Text on Windows
- **Decision:** native **DirectWrite** layout and shaping (bidi, fallback, variable fonts), Direct2D grayscale
  rasterization; Core stores text data only; saved pixels stay authoritative until the text is edited; an Apple→Windows
  font map (e.g. Apple SD Gothic Neo → Malgun Gothic) used only for missing faces and reported to the user; golden
  metric tests bound differences.
- **Why:** best system-font, Korean IME and rendering quality on Windows; identical cross-platform layout would need
  HarfBuzz/FreeType and lose native integration.
- **Windows:** DirectWrite caches layouts and glyphs; no per-frame re-layout. **macOS:** Core Text unchanged.
- **Migration:** wave 3/7 (text style is data; engine is platform). **Reversible:** Yes (behind the text-engine
  interface).

### Q10 — Color management on Windows
- **Decision:** **LittleCMS 2** (vendored, pinned) for import/export/display conversions; the exact ICC profiles macOS
  uses for each `ColorSpaceID` exported from `CGColorSpace` and shipped; compositing in the document's encoded space
  (as macOS); display via a 3D LUT from the monitor profile; CMYK edited as sRGB and converted on JPEG export (as today);
  tests require ΔE2000 ≤ 1 against ColorSync.
- **Why:** deterministic, identical-profile conversions on every Windows machine; the Windows Color System APIs don't
  offer the transform control an editor needs.
- **Windows:** conversions happen at import/export and in one GPU pass for display; never per frame on the CPU.
  **macOS:** ColorSync unchanged; the process-wide `WorkingColorSpace` becomes a per-document input in the Core (Q25).
- **Migration:** Wave 0 exports the profiles; wave 4 replaces `DocumentColorProfile`'s `CGColorSpace` lookup side.
- **Reversible:** Yes (engine behind the platform layer); shipped profiles **Costly** (changing them changes colors).

### Q11 — Core language
- **Decision:** **C++20 Core; C11 pixel kernels stay; C ABI boundary.** See windows-architecture.md §1 for the
  evaluation against the nine priorities.
- **Why:** Windows performance and toolchain maturity (priorities 1, 4, 6, 7, 9) outweigh Swift's advantages (safety,
  existing code); the safety gap is closed with fail-fast rules, hardened libraries, sanitizers, fuzzing and
  differential tests.
- **Windows:** native code, no language runtime, first-class tooling. **macOS:** Swift UI and Metal renderer stay; the
  Core is called through a C ABI at bulk granularity.
- **Migration:** Core track (implementation-plan Waves 1–2+), with differential tests against the Swift model.
- **Reversible:** Yes until Wave 2 begins; **Costly** after.

### Q12 — C ABI generated or hand-written
- **Decision:** the **C header is hand-written** and is the reviewed source of truth; **C# P/Invoke bindings are
  generated** from it at build time (ClangSharp's P/Invoke generator, pinned); the Swift side imports the header
  directly through a module map, with a thin hand-written Swift wrapper for ownership (`deinit` → release).
- **Why:** the header is the contract and deserves review; the spike showed four hand edits per function when bindings
  are hand-written.
- **Windows:** blittable structs and arrays only across P/Invoke (no marshaling allocations). **macOS:** zero-cost C
  import. **Reversible:** Yes.

### Q13 — Process model
- **Decision:** **in-process** Core, fail-fast on internal invariant violations, autosave/recovery (Q14).
- **Why:** out-of-process would put every snapshot and image behind IPC and shared memory for a benefit (surviving
  Core faults) that autosave largely delivers.
- **Windows:** zero IPC on hot paths. **macOS:** as today. **Reversible:** Costly.

### Q14 — Autosave / crash recovery
- **Decision:** a platform-layer autosave job writes a snapshot of each modified document as an ordinary `.comp`
  package to a recovery folder — `%LOCALAPPDATA%\Compositor-KR\Recovery\<DocumentID>\` on Windows,
  `~/Library/Application Support/Compositor-KR/Recovery/` on macOS — after 60 s of idle time with unsaved changes,
  on a worker thread from a snapshot; offered for restore at the next launch; deleted on save or discard.
- **Why:** the only defense against in-process faults (Q13) and power loss; reusing `.comp` needs no new format.
- **Windows:** off the UI thread; writes only changed layer PNGs after the first time (content hashes). **macOS:** new
  behavior, introduced only when the Core is (not in Waves 0–1). **Reversible:** Yes.

### Q15 — Thread-affinity enforcement
- **Decision:** always checked, in release too: every mutating entry point compares the calling thread with the
  document's owner thread and returns `wrongThread` otherwise.
- **Why:** a thread-ID compare costs about a nanosecond; a silent data race costs a corrupted document.
- **Windows/macOS:** negligible. **Reversible:** Yes.

### Q16 — History budget
- **Decision:** keep today's values on both platforms — 100 steps and 256 MiB of pixels retained only by history —
  counted per unique tile, so shared tiles aren't double-counted. Revisit only with measurements on large documents.
- **Why:** preserves current behavior; tile sharing already makes the budget go further than today's whole-image count.
- **Reversible:** Yes (settings value).

### Q17 — Windows UI technology
- **Decision:** **WinUI 3 (Windows App SDK, stable releases only) with a C# application shell** for the Wave 1
  prototype; the canvas is native C++ Direct3D 11 in a `SwapChainPanel`. It becomes final when the prototype meets the
  canvas targets (60 fps panning a 10,000 × 10,000 document with 200 layers on the reference machine, layer panel
  refresh < 16 ms at 2,000 layers). If it doesn't, the fallback is the same native renderer hosted in a Win32 window
  with C++/WinRT UI — the Core and renderer are unaffected either way.
- **Why:** the WinUI 3 test showed no fatal issue; the hot paths are native, so the UI language doesn't limit
  performance; C# gives UI productivity.
- **Windows:** UI thread never renders; all heavy work native. **macOS:** none. **Reversible:** Costly (UI rewrite), Core
  and renderer unaffected.

### Q18 — Windows App SDK deployment
- **Decision:** **self-contained** (bundled in the MSI; nothing to install separately), referencing only the component
  packages the app uses (WinUI, Foundation, Base, InteractiveExperiences, DWrite) instead of the metapackage, which
  drops the ~47 MB of AI/ML/Search components. Stable versions only, pinned.
- **Why:** one MSI with no prerequisites; the smaller payload shortens every update download.
- **Reversible:** Yes.

### Q19 — .NET and VC++ runtimes
- **Decision:** .NET 10 published **self-contained** with ReadyToRun (Native AOT evaluated in Wave 1 — the Windows App SDK
  supports it — and adopted if startup and size improve); our native DLLs link the **static CRT**, so no VC++
  redistributable is needed and no app-local VC++ files are shipped.
- **Why:** no prerequisites for users; static CRT is safe here because no CRT object crosses the C ABI.
- **Windows:** faster startup (R2R/AOT). **Reversible:** Yes.

### Q20 — Windows renderer
- **Decision:** **Direct3D 11.1** (feature level 11_0 minimum) + **Direct2D** on the same device + DirectWrite + WIC;
  DXGI flip-model swap chain; HLSL shaders matched to the Metal/Core Image output by golden images.
- **Why:** see windows-architecture.md §2.3 — simpler and equally effective for a few-pass 2D editor, native D2D/DWrite
  interop, full compute support.
- **Reversible:** Costly (renderer rewrite), no Core impact.

### Q21 — Vision features on Windows
- **Decision:** behind a platform `SubjectSegmenter` interface, implemented on Windows with **ONNX Runtime (DirectML
  execution provider, CPU fallback)** and a permissively licensed segmentation model shipped with the app; it produces
  a `CorePath`/mask like the macOS Vision path. Scheduled after core editing parity; Windows ships without Object
  Selection/Subject Removal until then, with the commands hidden rather than broken.
- **Why:** works on any DirectX 12-capable GPU (not only NPU machines, as the Windows AI APIs require) and keeps the
  model under our control.
- **Reversible:** Yes.

### Q22 — Syncing `main`
- **Decision:** after every `main` release (each version tag), within the same week, following AGENTS.md rules 11–20;
  done for 1.4.5 on 2026-09-30.
- **Why:** small, frequent syncs; 1.4.5 already showed that a release can reintroduce Apple-only code (Scanlines'
  blocks), which is cheap to fix when caught at once.
- **Reversible:** Yes.

### Q23 — Where the spike lives
- **Decision:** `spike/core-model` stays as a frozen branch (no further commits), tagged `spike-core-model-final`
  when the Core's Wave 2 differential tests pass; its findings are already in
  [spike-findings.md](spike-findings.md) on this branch.
- **Reversible:** Yes.

## New questions found while deciding

### Q24 — `.comp` is a folder on Windows
- **Finding:** `.comp` is a macOS document *package* — a folder. Windows has no packages; a `.comp` is an ordinary
  folder, which can't take a file association.
- **Decision:** keep the format (no change). The Windows app opens projects through a folder picker, drag and drop, and
  a shell verb "Open with Compositor-KR" registered by the MSI for folders whose name ends in `.comp`. A single-file
  container would be a format change and is out of scope.
- **Reversible:** Yes.

### Q25 — Process-wide working color space
- **Finding:** `ColorProfile.swift` (split into Core/Apple layers by 1.4.5's 3672e7f) keeps `WorkingColorSpace`, a
  process-wide current profile behind `NSLock`, read by buffer-making code on any thread.
- **Decision:** the Core has no such global; every operation that makes pixels takes the document's `ColorSpaceID` (or
  gets it from the snapshot). On macOS the global stays until the Core replaces the code that reads it.
- **Windows:** no lock on the pixel-creation path. **Reversible:** Yes.

## Still open

None that blocks Wave 0 or Wave 1. Two decisions are provisional by design, each with its finalizing condition:
Q17 (WinUI 3 — the Wave 1 prototype meeting the canvas targets) and Q19's Native AOT (measured in Wave 1).
